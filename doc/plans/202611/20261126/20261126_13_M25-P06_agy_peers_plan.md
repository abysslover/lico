## What this phase makes

P02 to P05 made `agy` a session of the host that a person can start, resume and see. This phase lets it talk to the other sessions the way Claude and Codex do: Send to, an `@name` of the person, a Call Room, a reply that returns to the one who asked.

The exchange machinery of the host (`calls.rs`, `mention.rs`, `call_room.rs`) was written for `claude` and `codex`, each of which has a tool (`mcp__lico__send`). `agy` has none (decision D4: its tool servers are empty, the program is given no tool of Lico's). What it has is the turn: it is given a prompt, and what it says in answer is a record of the host. The two things the machinery needs from a program are therefore already there since P02: the answer of a turn is fed to `peer_turn` (`push_line`, `finish`, `drop_active`) and a finished turn hands its reply to `deliver_peer_reply`.

1. **One question, one place**: `calls::takes_part(provider)` (`claude`, `codex`, `agy`) replaces the six places that asked `matches!(provider, "claude" | "codex")`: the target check of a tool's `send`, the note of an outbound call (`before_peer_deliver`), the two "both are provider sessions" checks that record a reply and a transfer in the Call Room, the named-peer lookup of `@name` and the scan of an answer for `@name` paragraphs. `local` and a session with no provider are still no peers.
2. **A deferred reply**: `try_defer_peer_reply` counts a session with a driver as one that can take a reply later (`has_sink`), so a reply that arrives while an `agy` session is busy waits for the end of its turn (`flush_deferred` already sent it to the driver's link) instead of being refused.
3. **The Call Room knows `agy`**: `call_room::normalize_provider` keeps `agy` (it was filed as `synthetic`), so a room between two `agy` sessions says `agy` for both and its entries are recorded under that provider.
4. **How `agy` sends**: a program with tools is told, after an inline `@name` of the person, to call `mcp__lico__send`. `agy` cannot, so `calls::mention_hint` tells it the other way, in the same words of authorization: a paragraph of its answer that begins with `@name` at the start of the line is sent to that session at once (`mention::dispatch_assistant_mentions`, the same keep, the same room, the reply returns). The room's envelope already says that an ordinary reply of the turn is recorded automatically, which needs no tool.
5. **Not changed**: `session.rs` (800 lines), `core.rs`, `folders.rs`; the window (the Send to menu, the mention list and the room view are written over the sessions' own provider text and needed no change; the tests below prove the host side and the window shows what the host records).
6. **Not supported, as for Codex**: handing over a whole conversation (`transfer.hand_over`, `recorded`) is for a Claude conversation only (`bad_request`); an `agy` conversation is not read out of its program's files by the host, so Send to with a text or lines is the way to give it something and to take something from it.

## Personal data and security

- The only text this phase adds for a program is the host's hint. It names the session's label and id as the existing hint did and carries no path, account or secret.
- An answer of `agy` is scanned for `@name` paragraphs exactly as the answer of a Claude or Codex session is: the same resolution of a name to a running provider session, the same keep (the person's authorization of the room, or an approval card), the same limits (rounds, deferred replies, calls per minute). A program that answers with a `@name` paragraph by its own choice sends what any other program could send; nothing is sent to a session the person did not make a room with or approve.
- `local` sessions stay outside: a model of the person's own that has no tool and no reviewed way to be told is not given a place in an exchange.

## Not decided here

How the real program answers the hint (it may put the `@name` in the middle of a line, or quote it; only a paragraph that begins with the name is a send); handing over a whole `agy` conversation; an attachment to an `agy` session; whether the owner wants `agy` to be told about the other sessions it may call (the room's envelope names the other session; a list of callable sessions is for the tools of the others). All of it needs the real program, gate G3.

## Results (2026-11-26)

What was made: see the list above. The host's machinery needed no new path: five of the six places only had the word list, the sixth (`has_sink`) did not know the driver, and `normalize_provider` filed `agy` as `synthetic`. The hint is the one new text.

### Tests (against the owner's budget of about 100 unit tests per turn)

- 2 new unit tests in `calls/tests.rs`: the hint after an inline `@name` (the tool for Claude and Codex, the paragraph rule for `agy`, the same id, room and closing sentence), and a send to an `agy` session by a tool (the outbound call is noted, the peer turn begins, the room records the send, an explicit reply of the `agy` session is recorded and delivered). 2 existing unit tests were extended: the provider gate of `send` (`agy` yes, `local` and no provider no; `takes_part` says the same) and the deferred reply of a driver session (`driver_hubs_tests.rs`: a busy driver takes a peer's reply to say later).
- 2 new host tests (`tests/test_agy_peers.py`, listed in `tests/testmap.toml` for `host` and in the rule of `src/host/adapters/agy/**`): Send to and a room between two `agy` sessions (the text is a prompt and is said as sent, the room's envelope reaches the second, its answer is recorded as a reply of `agy`, comes back to the asker, the room names both as `agy`), and an inline `@name` (the prompt carries the paragraph hint and no tool name; a paragraph of the answer that begins with the name reaches the other session and its answer comes back).
- The unit tests of the touched modules (`calls::`, `driver_hubs`, `mention::`, `call_room`): 40 passed. The two host tests: 2 passed.

### Mutation checks

14 mutants, one edit each of `calls.rs`, `mention.rs` or `call_room.rs` (the script and the logs are in the session's scratchpad, not in the repository):

- **Round 1: 10 killed, 3 survived, 1 did not build.** The survivors were `begin_call` not for `agy`, the explicit reply not recorded for `agy` and the transfer not recorded for `agy`: no test reached the hooks of `transfer::send` for an `agy` target (the host tests use `transfer.send` and a room, not a tool's `send`, and an `agy` session has no tool). The build error was a mistake in the text of the mutant (unbalanced parentheses), repaired.
- **Answered with a stronger test**, not by excusing them: the second new unit test above (a tool's send to an `agy` session, with the peer turn, the room's record and an explicit reply, which needed `keep` at the first send and a busy asker for `peer_reply_authorized`), and one more assertion in the host test (`from 'Bee'` reaches Ann's transcript, proving that the send began a call).
- **Round 2 (7 runs): all 14 distinct mutants killed.** Three by the host tests and the unit tests (`begin_call`, the answer scan), three by the unit test alone. Two extra runs of the host test against the explicit-reply and the transfer mutants *survive by reach*: those two hooks belong to a tool's `send`, which an `agy` session cannot call (no tool of Lico's, D4), so the host tests cannot reach them; the unit test kills the same edits.
