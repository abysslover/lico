## 1. What changes for the person, in plain words

- Nothing, unless a local session is made. With P06 a local session can be made from the command line and over HTTP (the window waits for P07): `lico session create --kind local --endpoint 127.0.0.1:11434 --api ollama --model NAME [--context N] [--name NAME]`. It has no account and no provider program: the host itself asks the model server on this machine, keeps the conversation in an owner-only record, and runs Lico's tools for the model with the approvals the other sessions have (three tools unasked, every other tool leaves its card, a waiting tool ends the turn, the decision comes back as a message). It has no file and no shell access. Claude and Codex sessions are untouched and never go to a local model.
- A server key (if the server wants one) is stored only in the OS keyring: `lico local-key set ADDRESS:PORT` reads it from standard input (never from an argument), `lico local-key clear ADDRESS:PORT` removes it. The host reads it for each request and sends it only as `Authorization: Bearer`; it is never logged, recorded or shown.
- `session.close` ends the work and keeps the record; `session.resume` reads the record again (also after a restart of Lico); `session.purge` deletes the record with the session.

## 3. The driver port (keeps the new kind out of the 48-module cycle)

**Why.** Today a session's provider is a string and the hubs branch on it at about a dozen places (`core.rs` 7 lines, `folders.rs` 2, `calls.rs` 2, `lifecycle.rs` 1, `new_session.rs` 1; every `else` means Codex). If the hubs named a `local` module, that module (which must use `core`, `session`, `tools`) would join the cycle. So the hubs call a **port** and the adapter registers itself.

**The port** (a new module `driver.rs`, std only, no `crate::` path: it depends on nothing; layer 0):
`trait Link: Send { send_input(&mut self, request_id, text) -> Result<(), &'static str>` (queues; never blocks, never locks the session)`; stop(&mut self); purge(&mut self) }`; `trait Driver: Send + Sync { kind() -> &'static str; start(&self, shared: &Opaque, session: &Opaque) -> Result<Box<dyn Link>, &'static str> }` with `Opaque = Arc<dyn Any + Send + Sync>` (the host's own types, which the adapter knows and downcasts; the port names none of them); `struct Target { addr: SocketAddr, api: Api, model: String, context_tokens: u32 }` (plain std types); `register(Arc<dyn Driver>)`, `get(kind)`. The adapter `local` is registered once, by name, in `unified.rs` (the root, which nothing uses).
**New edges** (all down to layer 0, none into a hub from below): `session`, `core`, `calls`, `lifecycle`, `folders`, `new_session`, `registry`, `ipc`, `unified`, `local` -> `driver`. The adapter `local` uses `core`, `session`, `tools`, `keyring`, `leads`, `lines`, `codex` (its text cleaning), `driver` and the four components, and **nothing in the cycle uses `local`**, so the strongly connected component stays at 48. This is checked, not assumed: `cargo xtask graph` before and after (a test of the tools' kind reads the JSON: the cycle has 48 modules, `local` is not in it, its only importer is `unified`). I will report the hub fan-in before (core 41, session 35, folders 22, transfer 15, codex 17, handoff 7) and after: the adapter adds one importer to each hub it uses (core, session, codex; not `folders`, `transfer`, `handoff`); that is the honest price of an adapter, as `claude.rs` pays 17.

**The hub touches** (each small, each with a test through a dummy driver, so the hubs are proved without the adapter): `Session` gets `driver: Option<Box<dyn driver::Link>>` and `Settings` gets `target: Option<driver::Target>`; `core.rs` start/resume/input/answer and `lifecycle.rs` close/purge call the link when the session has one (before the Codex `else`); `calls.rs` `flush_deferred` likewise; `folders.rs`/`new_session.rs` start a driver session; `registry.rs` accepts `local` and saves and restores its target (a local session has no account); `ipc.rs` accepts the kind and validates `endpoint` (loopback only), `api`, `context_tokens`; `cli.rs` the flags and `local-key`. The sites that read `provider == "claude"` for chats, login, accounts and clipboard are audited one by one (about 14) and the report lists each as "unaffected" or "changed".

## 4. The adapter `local` (inside the program, `src/host/hostd/src/local/`)
One worker thread per running session (none when idle). It implements the ports of `toolloop`: `ModelPort` (encode with `llm-wire`, `llm-http` with a `Cancel`, decode; the key for the request from a `KeyPort`; `fit` before each request and a log line "N oldest turns are no longer sent to the model" when the number grows; a message that alone is over the window is refused with the figures; a server's `tools` refusal on the first request is retried once without tools and the session is chat only, said in the log; the context size and tool support asked of Ollama through `show` when the person did not give one, else 8,192); `ToolPort` (the host's `tools::run` with the session as caller; an answer whose JSON says `"status": "pending"` is `Waiting`, an error is `Refused`, a picture block becomes a plain sentence); `RecordPort` (`lico-convo` in `registry_dir/local/<id>.jsonl`); `Env` (cancel flag and clock). Text is cleaned with the host's existing cleaning before it reaches the log (the lines go through `leads::agent_record`), the person's own message and the host's notices arrive through the existing `input` path. `KeyPort` has the real keyring behind it and an in-memory one for tests (no test touches a real keyring).

## 5. The system tests (a short named list in one place)
A file `tests/system_tests.toml` (name, why it is on the list, budget 512 MiB and 60 s, measured peak and time) and a small command `cargo xtask system [--record]` that runs each alone with the tree's memory sampled, as `cargo xtask test` does for a component (a test of the tools first). Four tests in Rust, each starting the real `lico` binary on a private home and socket with the P04 fake server as the model (no real server, no keyring, no billable turn): **S-1** a message through a local session streams lines into the log; **S-2** a tool that needs a card waits, the person allows, the result comes back as a message and the answer ends; **S-3** a stop cancels a running stream within about a second; **S-4** the server vanishes, the session says so and recovers on the next message. Why they are on the list: each needs the real process boundary (the host binary, its socket, its registry and log) that no component test has; they are few because the components already carry the logic.
