## Goal

A person can capture the screen, a window or a region, copy and paste text and an image with the window, paste an image into the input box so that it reaches the agent with the next message, and an agent can ask for a capture through the tool connection of P03. A screenshot never vanishes from the record without a trace. The work is X11 only; the X server and its version are written in the report.

**Order of the steps:** S01 (the provider line reader, XF-08; the measured data loss comes first because everything after it returns images through that line), S02 (capture core and command, XF-01 to XF-03, MB-03; built in two parts: S02a, the PNG encoder and its proofs with no X11, and S02b, the screen read, the shrink and `lico capture`), S03 (the helper process, XF-07), S04 (clipboard, XF-04, SF-06; built in two parts: S04a, the read side of the clipboard and the move of the selection code, and S04b, the write side through the window and the setting; both are built), S05 (image paste, XF-05), S06 (middle-button paste, XF-06), S07 (the agent tools and a row for the real program, SF-06), S08 (the memory measurement against MB-03, the report and the try-it text of P03 and P04 together). Each step: a red test first, then green, one commit, one short mail to the lead.

## What exists already (read on 2026-10-29)

- `core::bounded_lines` (`core.rs` 282) drops a line over its limit whole; `claude.rs` (limit 256 KiB) and `codex.rs` (256 KiB) read the program's output through it. A dropped line is not counted and not recorded: nothing is left in the record (XF-08, *measured* 6 of 6).
- `claude.rs` `handle` turns a tool result into `> ` lines through `text_of`, which keeps text blocks only: an image block of any size gives no line at all, so even a small image leaves no trace.
- The real program's own record file (2.1.310, read on this machine for its shape only, no content kept) has an image result as one line of about 110 to 150 KiB at 1200 x 800: the image data sits twice in it (`message.content[].content[].source.data` and `toolUseResult.file.base64`), and `media_type` comes after `data`. A window capture at 1080p is several times larger. The first 8 KiB of such a line holds `"type":"image"` but neither the size nor the type.
- Text paste exists: `fetch_selection` and the owner of the selection in `gui/ui.rs` (about lines 1150 to 1305), Shift+Insert reads PRIMARY, Ctrl+V reads CLIPBOARD, an incremental transfer is refused. There is no middle-button handling and no image path. `x11rb` 0.13.2 (core protocol only, no extension feature) is a dependency; no deflate or PNG crate is in `Cargo.lock` or in the offline cache.
- The tool connection (`tools.rs`, `mcp.rs`) answers with one text block; every argument is a string. `exp/202610/20261026/00001_real_program_canary` is the opt-in canary for the real program.
- Test displays: `lico_measure.rig.Xvfb` starts a private server; `xdpyinfo`, `xclip`, `xsel` and `xdotool` are installed for fixtures.

## S01 - the provider line reader (XF-08; host only)

- **Probe first (one haiku turn, opt-in, the canary's way):** the real program reads a PNG of about 300 KiB; I keep the size of the line it writes on stdout and where the image data sits, outside git. The red test uses that shape. Nothing about the real program's stream is claimed before it.
- **Red test:** a provider line over 256 KiB that holds an image result (the shape above) leaves a record `[image N KiB omitted]` for the image and the rest of the line (text after it, the tool result's other blocks) as before; today it leaves nothing. A line with a small image gives `[image N KiB]`. The record holds no path of the provider's folder. A line that is not JSON or is still over the limit after the strings are cut gives `[line N KiB omitted]`.
- **Change (as built, 1.0.1):** the reader moves out of `core.rs` into `lines.rs` (`lines::lines` for the host's two providers, `lines::read_line` for any reader of lines, `lines::plain` for the plain synth agent as before). A line at or under the limit comes byte for byte. When what is held goes over the limit, the string being read (or else the longest string already read) is cut to its first 4 KiB and a mark with the number of bytes left out; a line that is still over the limit is `[line N KiB omitted]`. Memory is the limit plus the marks. `claude.rs` renders image blocks as `[image N KiB]` or `[image N KiB omitted]` and a cut text as its head with the note `[N KiB omitted]` on a line of its own; a permission or approval request that holds a cut is refused to the provider and never put to a person. `provider_record` (P03, the second reader of provider lines, record FILE, 4 MiB) uses the same cutter. Loops: 20 runs of each new test; the reader is also run on a 64 MiB line with a memory check.
- **Not claimed:** what Codex prints for an image (shape-agnostic by the cut; no real-program row for it in this phase).

## S02 - capture core and command (XF-01 to XF-03, MB-03)

- **Command:** `lico capture` with `--screen` (default), `--window <id>` or `--region x,y,w,h`, `--out <file>`; the answer is one JSON line: `path`, `width`, `height`, `bytes`, the server (vendor and release from the connection setup), for a region its `offset` and `scale`, and the agent copy (`agent_path`, size, `scale`) shrunk to at most 1568 px on the long side. A click on the agent copy at (cx, cy) is the screen point (x + cx/scale, y + cy/scale); a test pins this with a fixture where a shrunk and an unshrunk region differ.
- **Red tests (E, Xvfb 1920 x 1080 with a known pattern):** the full capture has the pattern's pixels at known places (read back with a small decoder in the test, not the product); a region returns the offset and scale of its coordinates; a window capture is the window's rectangle on the screen; an agent copy of a 1920-wide capture is 1568 wide.
- **Bands (XF-03):** the screen is read with `GetImage` a band of rows at a time (about 256 KiB per band) and shrunk on the way (box filter, row accumulators), and the PNG is encoded row by row into the file. **Measured in S08, written in the report:** the peak of the helper's resident memory (VmHWM) minus its resident memory at start, at 1080p, against the 6 MiB of MB-03.
- **PNG without a dependency:** the encoder (filter, a small LZ77 with fixed Huffman codes over a 32 KiB window, CRC and Adler) is written here; see Deviation D2. The compression ratio on a text screen and on a photo is measured against `import` and written.

## S03 - the helper process (XF-07)

- Every X job (capture, clipboard read, clipboard write for the command line) runs as `lico` called with a hidden job name, started by the host or the command, writing its answer on stdout and ending; the long-lived host holds no X connection. **Red tests:** after a capture the host has no child and no more threads or open files than before (read from `/proc`), and its resident memory is within the noise of before; a job that hangs is ended by its deadline and the caller says why.
- **Built (1.0.4):** the job side is `xjob.rs` (a table of jobs, one line each; `capture` is `capture::command`; no usage text or README names it), the host side is `helper/mod.rs` (`run_job(bin, job, args, limits) -> Result<Value, JobError>`; the program is the field `job_bin` of the host configuration, default the running program, flag `--job-bin`). Nothing calls it yet (S04 and S07 do); see Deviation D8.

## S04 - clipboard (XF-04, SF-06)

- **Read** (text or `image/png`) is done by the helper with a connection of its own, as `fetch_selection` does, and fails with a reason: `empty`, `timeout`, `too_large`. **Write** needs an owner that lives, so it is a request to the window (an event on the connection the window already has); with no window connected it fails with `no_window`. **Red tests:** E with `xclip` as the reader of what the window wrote (text and image) and as the writer of what the helper reads; `no_window` without a window.
- **Off by default (SF-06):** the agent tool `clipboard_write` is not in the tool list until the person switches it on; the command line, run by a person, writes. The setting and its default are tested.
- `gui/ui.rs` (1,305 lines, may not grow, TST-07): the selection code moves to `gui/clip.rs` in this step, so the file shrinks.
- **Built, S04a (1.0.5):** the move came first as a commit of its own (`gui/ui.rs` 1,305 to 1,209 lines, `gui/clip.rs` 105, `gui/mod.rs` unchanged at 816; no behaviour change, the paste and copy tests are green before and after). The read is the module `clipboard` (`clipboard/mod.rs` the reader `read_selection`, which returns a value; `clipboard/job.rs` the command `lico clipboard read` and, the same function, the hidden job `clipboard_read` of the table in `xjob.rs`); see Deviation D9. The window still pastes through `fetch_selection` (text, 500 ms, INCR refused); S05 switches the window to the new reader for images. S04b (the write side, the setting `clipboard_write`) is built, see the next bullet.
- **Built, S04b (1.0.6):** `lico clipboard write (--text STRING | --text-file FILE | --image FILE) [--timeout-ms N]`. The host relays the request (op `clipboard.write`, pushed event `clip.write`) to the newest window that attached a view of kind `gui`; the window owns the CLIPBOARD selection (`gui/clip.rs`: targets, refusal of the other form, incremental transfer, release on SelectionClear) and confirms with the op `clipboard.done` only after `get_selection_owner` says its helper window owns it. Reasons: `no_window`, `timeout`, `too_large`, `bad_image`, `write_failed`, `x_error`, `usage`; exit 0, 1 (usage), 2 (other), 3 or 4 (no host). The module `clipboard` gained `open` (the safe open), `settings` (`clipboard_write_enabled`, for S07, called by nobody yet) and `write` (the command); the host side is the module `clipwrite`. `gui/ui.rs` 1,209 to 1,204 lines, `gui/clip.rs` 105 to 411, `core.rs` unchanged at 1,088. No agent tool is built; a test pins that the tool list holds no `clipboard_write`.

## S05 - image paste (XF-05)

- **Window:** Ctrl+V asks the clipboard for its targets; with `image/png` the image is fetched (an incremental transfer is accepted for the image, with a limit of 3 MiB and a deadline), the input box shows an attachment chip with its size, and the next message carries it. A larger image, a format other than PNG or a picture over 8000 px (read from the PNG header, no decoding) is refused with a notice in the box. The picture is held in the window until it is sent or removed (Escape on the chip): part of the temporary +6 MiB.
- **Host:** the image goes into a private file of the host's folder (mode 0600 in a folder 0700, never in the repository, SF-04) and the `input` request carries the file's name, not the bytes (the request limit is smaller than the image). `claude.rs` `send_input` builds the user message with an image block (base64, media type, then the text); the file is removed when the message is sent. The protocol note gets the new field.
- **Red tests:** P (host, no display): an `input` with an attachment gives a provider message with the image block in front of the text and the file is gone afterwards; a wrong name, a file over the limit or a path outside the folder is refused. W (window dump): the chip and the notices. E (one): Ctrl+V of an image set with `xclip` attaches it. **Not claimed:** that Codex takes the image; the step asks the real program (Claude) in S07's row and tries Codex only as a probe.

## Deviations (for decision)

1. **D1, XF-08 cuts strings, it does not keep the first 8 KiB (accepted in mail 116, with conditions; done in S01).** The requirement says the line is read as a stream that keeps its first 8 KiB or so. In the real record shape the image is in the line twice, `media_type` comes after the data and other blocks may follow it, so the head cannot tell the size or the type and loses what follows. Cutting every string over 4 KiB keeps the structure, gives each image its size and holds the same bound on memory. The record text is the one the requirement names (`image N KiB omitted`, `[image]`). The answers to the conditions: a line at or under the limit is not touched (a test compares a 240 KiB text line, and the Python test a 200 KiB text result, with what the old reader gave); a string over the limit keeps its first 4 KiB, never ends inside an escape, a character or a surrogate pair, and its note is `[N KiB omitted]` on a line of its own (a record line is clipped at 4,096 bytes, so a note on the same line as a long head would be cut off); the image size is `lines::image_line`, `data.len() / 4 * 3`, for the host and for the record file (one function, not two); the second reader, `provider_record` (record FILE, `MAX_LINE` 4 MiB), used to skip a line over 4 MiB whole (a 1080p capture, the image twice, gave the receiver of "send conversation" only `Skipped: 1 line over 4.0 MiB` and no word of that message) and now uses the same cutter: the capture shows as `[image N MiB]` (`omitted` when its data was cut), the text around it stays. One P03 test encoded the old rule and was changed with it (`tests/test_conversation.py`, the 20,000-line record): a text of 5 MiB is now shown as its first 4 KiB and `[5.0 MiB omitted]`, and a second line of 5 MiB that has no string to cut still gives `Skipped: ... 1 line over 4.0 MiB` (red on the old build, green on the new, 20 of 20).
2. **D2, no deflate or PNG dependency (own encoder decided in mail 116).** None is in the lock file or in the offline cache; adding a crate is a decision about the supply chain that is not mine. My default is an encoder of our own (about 150 lines, tested against `import` and a reference decoder in the test). If the lead prefers a crate, S02 changes and the rest does not. Decided: own encoder, no new crate, with four safeguards in S02: every PNG a test writes is read back by two independent readers (the test's own decoder and an outside program: ImageMagick or Python `zlib` with a chunk parser); the edges 1x1, width 1, height 1, widths that are not a multiple of 8, one colour, noise, a gradient, a text-like pattern and 1920x1080, and CRC32 and Adler32 against known vectors; a ratio floor, measured and written in the report (a text screen and noise, against `import`); a size guard: the agent copy of a worst-case (noise) 1920x1080 capture must fit what the provider takes for one image, the limit taken from the program (a probe) or its documentation with the source named, and the case over it gets the reason `too_large`, never a broken image block. If the encoder cannot meet the ratio or the guard, the lead is mailed before anything is widened.
3. **D3, paste does not decode or shrink.** There is no inflate in the product; the paste is limited by size and by the dimensions in the PNG header, and refused with a notice above them. A clipboard image in another format is refused.
4. **D4, a window capture is its rectangle on the screen.** What other windows draw over it is in the picture; capturing a covered window needs the Composite extension and is not part of this phase.
5. **D5, capture and clipboard read ask for approval per call.** SF-06 names control and clipboard writing; reading the screen or the clipboard shows the person's data to the agent, so it gets the approval that `send` has. D3, D4 and D5 are accepted (mail 116), with three small asks: S04 names the one place where the person switches `clipboard_write` on (the M02-P01 menu or the config file) and its red test covers it; S05 opens the pasted file without following a symbolic link and checks on the opened descriptor that it is a regular file of the user within the size limit; S07 says in its first lines which of the host's existing approval paths the tools use.
6. **D6, what S01 changes in S02 to S08 (found while building S01; no requirement is re-opened).** (a) The real stream was probed (one haiku turn): a PNG of 270,448 bytes (300 x 300, noise) gave one stdout line of 721,914 bytes, the data twice (`message.content[].content[].source.data`, then `media_type` after it, and `tool_use_result.file.base64`, snake case on stdout, camel case in the record file), so about 2.7 times the PNG; any PNG over about 95 KiB makes a line over the 256 KiB limit. S07's row must therefore choose the pattern by the size it wants: a PNG under about 95 KiB gives `[image N KiB]`, one over it gives `[image N KiB omitted]`; a plain test pattern is small and does not show the cut. (b) The cut changes only the record, never what the provider holds: an agent copy that is too big for the record is still seen by the provider, and a request to a person (S07 approvals) that holds a cut string is refused, so a `capture` or `clipboard_read` approval must stay small (arguments are short strings, so it does). (c) S02's size guard (D2) speaks of what the provider takes for one image; the record's own limit is a second, separate one and needs no guard. (d) S05: the host side of the attachment goes the other way (host to provider) and is not read by `lines.rs`; the provider echoes the user message on stdout with `isReplay` set (seen in the probe for a text message; whether it echoes an image block was not probed), and such a line would be cut like any other. (e) The file-size rule (TST-07): `core.rs` is now 1,088 lines (the reader left it) and still may not grow; `claude.rs` 477, `codex.rs` 595, `lines.rs` 555 (13 tests in it), `provider_record/tests.rs` 695. (f) S08: the whole-suite time moved by the figure in the S01 mail; the standing figures of S08 are taken after S01.
7. **D7, what S02b settled (no requirement is re-opened).** (a) The size guard `AGENT_LIMIT` is 7,500,000 bytes of PNG, taken from the Claude platform documentation page "Vision" (read 2026-10-29): 10 MB of base64 on the Claude API and on claude.ai, 5 MB of base64 on Bedrock; base64 is 4/3 of the bytes, so 7.5 MB of PNG is the first-party figure and a Bedrock provider would need 3.75 MB. The guard answers `too_large` instead of handing the file over. (b) Ratio against `import`: a real render is 2.56 times, noise is 0.999 times; a text-like screen of S02a is accepted at 40 times by the lead on 2026-10-29 in mail 120, after the measurement, pinned in `capture::tests_x`. (c) The Rust X tests of `capture` take about 12 s of wall time in the dev profile (parallel threads), over the 8 s asked; the number is in the slice mail.
8. **D8, what S03 settled (no requirement is re-opened).** (a) The host side reads the job's two pipes with `poll(2)` in the calling thread and starts no thread, so a thread that is not joined cannot exist; the property is read from `/proc` all the same (threads, open files, children, resident size) in a process of its own. (b) A job runs in a process group of its own; on its deadline, or when its answer is over the limit, the whole group gets SIGKILL and the child is reaped before the function returns; a job that ended but left something running in its group loses it too (the group id is used a moment after the child is reaped, which cannot belong to anyone else yet). A process that leaves the group on purpose is not reached. (c) `JobError.reason` is text, because a failure of the job itself (`{"ok":0,"error":R,"detail":D}` with exit 1 or 2) is passed through with its own reason; the reasons of the helper are `timeout`, `spawn_failed`, `output_too_large`, `bad_answer` and `killed`. (d) "Within the noise" for the resident size is a measured allowance: 20 runs of the same driver moved it by 0 or +192 KiB (one step of the allocator, never growing with the jobs), so the test allows twice that; children, threads and open files are compared for equality. (e) The unit tests that start the real program take it from `LICO_BIN` (the suite sets it to the release binary it built), see `tests/README.md`.
9. **D9, what S04a settled (no requirement is re-opened).** (a) The reader and the job live in a top-level module `clipboard`, not in `gui/clip.rs`: the reader is used by the window (S05), by the command and by the helper, and the area map of `tests/testmap.toml` (`clipboard = ["cli"]`) then runs the clipboard tests for a change of the reader without running every window test; `gui/clip.rs` keeps the window's own selection code, moved unchanged. `mod clip` is declared in `gui/ui.rs` with `#[path]`, as `row` and `reconnect` are, so `gui/mod.rs` stays at 816 lines. (b) Text is read as `UTF8_STRING`, or `STRING` when that is all the owner offers (the two forms `fetch_selection` asks for); a text of 0 bytes is `empty`; an owner that refuses `TARGETS` is asked for the wanted forms in turn (an image first for `auto`) and a refusal of all is `empty`. An owner that lists targets of which none fits is `unsupported_format`, so `empty` always means "nothing to read". (c) One deadline covers the whole read, from the connection to the empty chunk of an incremental transfer. (d) `--max-bytes` sets the limit of both kinds; without it text is 65,536 and an image 3,145,728 bytes (for `auto` the limit of the kind that is chosen); the flag takes 1 to 67,108,864 and `--timeout-ms` 1 to 600,000; `--out` with `--kind text` is a usage error (a text is in the answer, a file would be a surprise). (e) The picture is checked by its header only (signature, IHDR of 13 bytes, a side of 1 to 8,000; a side over 8,000 is `too_large`, a side of 0 or other bytes `bad_image`); the CRC of the header is not checked because nothing is decoded. (f) The answer line writes U+0085, U+2028 and U+2029 as escapes, because a line splitter of some languages cuts at them and the answer must stay ONE line for any reader. (g) `capture::out` is `pub(crate)` so that the picture is written by the same safe writer; nothing else of `capture/` changed.
10. **D10, what S04b settled (no requirement is re-opened).** (a) The host holds no X connection (S03), so the write is a relay to ONE window, the newest that attached a view of kind `gui` (a real window does so when it shows a session); the host answers the command only when that window confirms, and a confirmation with an unknown id, or from another connection, is refused and changes nothing. A request that is not confirmed within `--timeout-ms` (default 3000, 1 to 600,000) is forgotten, so a late confirmation finds nothing. (b) The window confirms only after `set_selection_owner` and a read-back `get_selection_owner == its window`; a second write replaces the first; SelectionClear releases the content; a request for the other form (text asked while a picture is held, and the reverse) is refused with property NONE. (c) A picture over the incremental threshold, the smaller of 256 KiB and the server's maximum request size less 1,024 bytes, goes by INCR: the size is announced, one chunk of at most 128 KiB per DELETE, then an empty chunk; a requestor that does not delete the property for 5 s is dropped and does not block a second requestor. (d) The safe open (`clipboard::open`) uses `O_NOFOLLOW | O_NONBLOCK`, judges the opened descriptor with `fstat` (regular file, owned by the user, size within bounds), reads at most max + 1 bytes and refuses a file whose length differs from the `fstat` size; a picture file is at most 3 MiB. (e) A text is at most 65,536 bytes; the request line is also checked against the host's limit of 262,144 bytes, because a control character costs 6 bytes of JSON escape, and the command answers `too_large` before it sends. (f) The setting `clipboard_write` is off by default and is read at each use from ONE file, `settings.json` beside the handoff folder of the host's state folder: at most 4,096 bytes, a regular file of the user that the group and others cannot write, a JSON object whose member is the boolean `true`; anything else (missing, unreadable, a string, a number, bad JSON) is off. Honest limit: a program of the same user that can write that folder can switch it on, as it could do other things as that user; the setting stops a tool from writing the clipboard unasked, not a hostile same-user program. (g) The setting governs the agent tool only (S07); the command run by a person always writes. S07 must add to the tool, on top of the op: an approval of the person, and the check `clipboard_write_enabled` at each call.

## Where this meets the code

## Tests and the test rules

- A wait in a test that hides a race says why it is there; a new test runs in loops before the done mail of its step; a test that depends on file modes or on the umask runs under 022 and 077; each test display is my own (`Xvfb` with a display number I got from `-displayfd`, on a private socket); I touch no X server that I did not start; the X server and version tested are recorded.
- The whole suite stays within 180 s with 3 workers. The fresh-clone first run was 187.4 s at `b35a156` (the Rust test target compiles from scratch); any step that adds more than a few seconds says the number in its mail.
- Heavy jobs go through `pri-heavy` with the label `lico`.

## Not in this phase
