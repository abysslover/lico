## Goal

A person, or an agent with the person's approval, sends text, selected lines or a whole conversation from one session to another. Up to 4 KiB goes inline with a header the host writes; longer goes to a file in the receiver's own handoff folder and the receiver gets a notice. Agents reach Lico through a tool connection served inside the host (no new process per session). The window shows who sent what (`from <name>`). Claude Code sessions only for the tool connection (SF-05).

**Order of the steps:** S01 and S01c (done), S02 (done, with two small items done), the V4 gate (done), S03a, S06, S03b, S04, S05, S07, S08 (report). The person-facing path comes first (transfer core, then the window modal), then the agent tools and their approvals. S06 does not need S03b: it calls the owner op `transfer.send` of S03a. Its "Hand over conversation..." entry is dimmed (`not available yet`) until S05 supplies the content; S05 enables it (a few lines in `gui/sendto.rs`).

## What S01 measured (AC-07; done 2026-10-26)

D3b is a **measurement, not a pass/fail**: each hold length was recorded as survived or dropped at N s; the stop line "two failed tries of the same case" belonged to the connection test only (5 of 5).

| `default` mode, no rule | 3 | 3/3 the program asked (`can_use_tool` on stdio) for `mcp__lico__<tool>`; its `ToolSearch` step was not asked |

**Protocol facts.** The program sends a `server/discover` probe (we answer HTTP 200 with a JSON-RPC error -32601), `initialize` (protocol 2025-11-25), `notifications/initialized`, a `GET` for a stream (405 is accepted) and `tools/list`; Host `127.0.0.1:<port>`, no Origin; the bearer header arrived every time; a new connection per request when the server sends `Connection: close`. A call that is still running shows in `stream-json` only as `tool_progress` heartbeats (30 s, 60 s, ...), which say "running", not "waiting for a person". **D3a:** pre-allow works, so Lico's approval can be the single prompt in `default` mode.

## What S01c measured (the premise of the busy-receiver rule; done 2026-10-26)

S01c is a second probe with the same harness (the real program 2.1.310, haiku, a private home, one folder; the throwaway code and the logs stay outside git; 9 runs, 7 valid). A second user message was written to the program while a turn was running, the way the host writes an input (one uuid per message, replay marks on); the model was asked to name the id in it. It is a **measurement, not a pass/fail**. Two runs were invalid and are not counted: the program blocks a foreground `sleep N` command, so the model started it in the background and the turn had ended before the message was written (a slow tool in a probe is a script).

| case | valid tries | result (*measured*) |
|---|---|---|
| m1: a 45 s script as the tool, permissions skipped, a message written 8 s after the tool call began | 2 | the program reports `queued` at once (its `command_lifecycle` event, keyed by our uuid); when the tool ends (37 s after the write in the longest try) the replay mark and `started` follow within 0.1 s, and the reply names the id: same turn, one `result` (2 turns), nothing lost |
| m1b: as m1, a second message 4 s after the first | 2 | both `queued` at once; two replay events (one uuid each) when the tool ends; one reply names both ids; one `result`; the two stay two inputs |
| m2: `default` mode, the permission answer held 15 s, a message written at 8 s | 3 | `queued` at once, nothing more while the answer is pending; after the answer: `tool_result`, replay mark, the reply names the id: same turn, one `result` |

A message written after a finished turn (the idle case, seen in the two invalid runs) starts a new turn at once. No error, no hang, empty stderr, about $0.004 per valid run. **Not tried:** a message written during a long model answer with no tool running (one try in the opt-in check of S04); an interrupt; other models or program versions.

## Decision: no tool call is held open; `pending` at once plus a wake-up input (AC-03, AC-07)

A tool that needs a person's yes returns at once; when the person decides, the host sends the outcome into the calling session as an input. Reasons: (1) a hold depends on things that can move (a per-server `timeout` or an env var of one program version; the limits of every other client, Codex's MCP client is not measured), while `pending` needs only a plain tool call and an input, which must work anyway; (2) a hold ends at its cap with "ask again" when the person is away for hours, which sends the model into a retry loop, and a wake-up has no loop; (3) the model does not poll: a model that ended its turn is woken, one that carries on gets the notice at its next tool boundary, in the same turn (the host writes the notice to the program at once, as for any input, and the program queues it and injects it there: *measured*, S01c); (4) S02's listener stays a plain JSON-RPC handler: no stream, no keepalive loop, no deadline below a limit, no "late answer ignored and the host cannot know", no held-stream cleanup at restart or purge. Cost: one extra turn when the person answers, only for the first approval of a kind (`keep: true` needs none after). `lico_check` is dropped. The measurements above stay here so that a later phase can add a bounded hold (S04b) if the extra turn matters; it is not part of P03.

## Security boundary (SF-08)

Approvals and per-receiver folders are consent and least privilege, **not a sandbox.** A session whose program has permissions skipped (the default for new sessions) runs shell commands as the user: it can read any file of the user (other inboxes and the token files included) and call the `lico` command line on the owner's socket as the owner does, `--from` included. What Lico does is stop *unasked* use of its own tool channel and show and log each such action (SF-01, SF-03). In a `default` session the program's own prompts gate the shell and every read outside `--add-dir`, so there the inbox split is a real boundary. The stop line "a file of one session's inbox readable by another" and its test are therefore scoped to what can be tested: the `--add-dir` argument that session's simulator is given, and `read_handoff`. No process-ancestry attribution is built: a detached program leaves the process tree, so it would be a boundary only on paper.

## S02 — the listener, the token and the list tool (AC-01, AC-05, AC-06, host only)

**Where it lives.** New modules `tools.rs` (listener, token table) and `mcp.rs` (JSON-RPC, tool schemas); `http.rs` is not reused as a route table (it is the owner's control surface behind the owner's credential; an agent must never reach its routes), but its small helpers (`read_request`, `respond`, `constant_time_eq`, the token bucket) become `pub(crate)` and are shared, no behaviour change there. One listener on `127.0.0.1:0`, bound **lazily at the first Claude session start** and kept for the life of the host; one accept thread with a 256 KiB stack, no timer thread; a connection cap of 32 as in `http.rs`; body limit 128 KiB (a 64 KiB text escaped up to 3x does not fit; see S03b); 5 s read/write deadlines; a failed-credential bucket. Expected cost: host RSS +0.2 MiB with 10 sessions (to be measured; stop line +2 MiB).

**Shape: plain JSON-RPC over HTTP, every handler answers at once.** `POST /mcp` only. `initialize` echoes a protocol version we know (2025-11-25, 2025-06-18, 2025-03-26; otherwise the newest); `notifications/initialized` gives 202, empty; `tools/list`; `tools/call`; `ping`; every other method, the `server/discover` probe included, gives HTTP 200 with JSON-RPC error -32601; `GET` and `DELETE` give 405 with `Allow: POST`. The Host header must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding); the program sends no Origin, so any Origin header is refused; the bearer is required (401 without). **Tools** (the program shows them as `mcp__lico__<name>`; names carry no second prefix): `sessions` in S02, then `send` (S03b), `create` (S04), `history` and `read_handoff` (S07). The names are one table in `mcp.rs`. **The definitions are paid in tokens in every session:** the `tools/list` result of the five tools is at most 2 KiB in all (one P test counts the bytes of the result, again as each tool is added).

**Token and config.** Per spawn and resume, 16 random bytes as key id and 32 as secret (`core::random_hex`), held only in memory in `tools.rs` as key id -> (session, generation, secret); compared in constant time; revoked when the provider process ends, the session is purged, or the generation moves on. The config file `<state>/tools/<session>.mcp.json` is created 0600 in a 0700 folder with `O_EXCL` before the spawn: `{"mcpServers":{"lico":{"type":"http","url":"http://127.0.0.1:<port>/mcp","headers":{"Authorization":"Bearer ..."}}}}`, no `timeout` key. It is passed as `--mcp-config <path>` (the token never enters the argument list, the environment or a log) and removed at provider exit, purge and host stop; the folder is emptied at host start. Not `--strict-mcp-config`: a developer's own tool servers keep working. **Every Claude session also gets `--allowedTools 'mcp__lico__*'`** so that Lico's approval is the single prompt in `default` mode (D3a); a simulator test checks the argument.

**What a local process can do.** One without the token gets 401 (throttled, 20 failures/s) and nothing else; for the rest see SF-08. `from <name>` is authentic against model output but not against a process that reads the config files.

Tests: U, one per shape above (initialize echo, 202, `-32601` for `server/discover`, 405, Host, Origin, 401); P (no model, the Claude simulator extended with `--mcp-config` and `--allowedTools`): initialize/list/call work; wrong Host 403; a token of an old generation 401 after resume; the token string appears in no log, no `ps` argument and no record; the file is 0600 and gone after purge; `sessions` returns id, name, kind, state, busy of the other sessions (no folder, no account, no history) without an approval. **Opt-in real-program check** (not in the suite; haiku, 3 tries: connects, lists, calls a tool; one try in each other permission mode 2.1.310 lists, "asks nothing" = pass; a slow tool in any such probe is a script, not `sleep N`).

## S03a — the transfer core (SC-04..06, SC-09, AC-04 counters; host + CLI, no listener needed)

New modules `transfer.rs` (send, header, limits, log) and `handoff.rs` (inbox, files, retention); one new owner op `transfer.send` {from, to, kind: text|lines|conversation, text} used by the window and the CLI (`lico session send ID --from ID2 -`; a person's own send has no `from` session). `from` is never taken from an agent's parameter: on the tool connection (S03b) it is the token's session.

**Rule.** The body is at most 4 KiB inline: the host delivers `[from session 'api-server' (a1b2c3d) | 14:02 | message | 1.2 KiB]` + a newline + the body through the same input path (so the echo of S02b records it: `echo::append` gets the header as its first record, `>> [from ...]`, and the body lines fold as today); a body line that itself begins with `[from ` gets one leading space so a body cannot pass as a second header. `Session::record_input` already runs once per accepted input under the session lock; it takes the **origin** (`Person`, `Agent(hops)` or `Host`, the last for the notices of S04) and sets `incoming_hops`; the three call sites in `core.rs` change in place, no growth (R5). Longer than 4 KiB (the limit counts the body only; after IN-01 the host accepts 64 KiB, so the threshold is a rule, not a limit) goes to the **receiver's own inbox**:

`<state>/handoff/<receiver id>/<YYYYMMDD>/<HHMMSS>_<from7>_<kind>.md`

The folder `<state>/handoff/<receiver id>` (0700) is made at session start, removed with the session on purge (SF-07: only what Lico made), and is the only handoff folder that session gets as `--add-dir` (claude.rs spawn, one argument). Files are 0600, written to a temp name and renamed, `O_EXCL`, with the file header of the screens note. No session can read a file addressed to another, including a whole conversation handed to somebody else (it may hold secrets), within the boundary of SF-08. This satisfies SC-05 as written (a folder under the state folder, 0700/0600, opened with `--add-dir`); it is a refinement. The receiver gets the notice: the header line, `Long content, saved as a file. Read it before you answer: <path>`, the first 3 lines (sanitized, at most 400 bytes), the reading hint (`N KiB, M lines; the Read tool refuses over about 25,000 tokens: read in parts with offset and limit, 400 lines at a time`) and `The file can be removed after 30 days.` The reply to the sender carries the delivery (`inline` or `file`), the size and the receiver's state. **Nothing is cut:** host-built content (the whole conversation, S05) over 32 MiB is refused whole (`too_large`) rather than written partly. New protocol errors, each a one-line addition: `send_limit`, `chain_depth`, `not_allowed`, `record_not_found`, `expired`; the others are existing names. CLI exit codes: 0 delivered, 2 refused with the error name on stderr (SC-04), 1 usage or connection. The CLI reads stdin with CRLF turned to LF (one test).

**The window's text beyond the limit.** The socket's request limit is 256 KiB and `valid_text` stops at 64 KiB (IN-01). Beyond 64 KiB the send is refused `bad_request` with a visible reason and the selection (or the draft) stays, as for IN-06. The whole-conversation path has no such limit because the host builds the content.

**Receiver states (new, not in the requirements).** *Idle or busy (a turn is running):* deliver; `claude.rs::send_input` writes the user message to the program at once and marks the session busy, and the program queues it and injects it at the next tool boundary of the same turn (*measured*, S01c); the reply says `busy` as information. *Waiting for an approval:* deliver, the reply says so (*measured*, S01c: injected right after the answer, in the same turn). *Disconnected:* refuse `session_disconnected`; Lico never resumes a session on its own (a resume starts a paid process). *Exited / unknown:* `session_exited` / `unknown_session`. **Nothing is queued by the host** (alternative: a per-receiver queue delivered on resume; rejected: state that survives restarts, surprising delayed delivery, memory). **What "delivered" means.** The reply says delivered when the host has written the message to the program (input state `accepted`); it does not say that the model has read it. For a mid-turn input the program's replay mark, which moves the input to `observed` and which the window never reads, comes only at the injection (37 s after the write in the longest try of S01c). The window empties its box at Enter, keeps a copy until the reply and puts the text back only on a refusal (`on_input_reply`), so that in-flight time shows nothing and needs nothing; the record shows the message at the write (the echo of S02b), above the tool output the model saw before it, which is the order of writing, not of reading. P03 changes none of this.

**Retention (SC-06), global:** at host start and after each file written, files older than 30 days go, then the oldest until the total is at most 256 MiB; no timer. **Transfer log (SC-09):** one line per transfer in the host's own log (from, to, kind, size, delivery, hops), never the body.

Tests: U (header escape, threshold at 4096/4097, retention arithmetic with fake times), P (inline; file; modes 0700/0600; the inbox exists at start and is gone after purge; **a file addressed to one session is not under the other's `--add-dir`**; each receiver state; exit 2 and nothing delivered; a person's send resets `incoming_hops`; log has no body; a selection over 64 KiB refused; CRLF). 9 tests, about 6 s.

## S03b — `send` on the tool connection and the limits (AC-04)

The tool `send` {to, text}: `from` is the token's session, never a parameter; it needs an approval (S04) and then goes through `transfer.send` of S03a. **What an agent's text may be:** up to 4 KiB inline, above that the host writes the file as in S03a; a text over the 128 KiB body limit is refused `too_large` with the reason ("split it, or write it to a file and ask the person"), never cut.

**AC-04, counted in the host and only in memory.**
- **Sends per minute:** 20 per calling session (sliding 60 s window; every authenticated `send`/`create`/`history` call counts, refused ones too), then `send_limit` with the seconds to wait.
- **Depth, D1 (a hop counter, so that a worker can answer).** Each session keeps `incoming_hops`: 0 when the latest input it accepted came from a person (window or CLI), otherwise the hops carried by the latest agent-sent message it accepted. An agent-sent message carries `hops = sender.incoming_hops + 1`; a send is refused `chain_depth` (the reason names both numbers) when that exceeds `MAX_HOPS = 4`. A, B, A, B, A runs and then stops; a person's input restarts the count; `create` counts as a hop; a retried request id changes nothing. **A host notice (S04) leaves `incoming_hops` as it is.** The AC-04 parenthesis ("an A to B to A cycle is stopped") reads "... stops at the depth limit" (recorded in the planning set). Alternative: the cycle list of the first draft; rejected, it forbids the main use (a worker reporting back).

Tests: reply works (hops 1, 2), the fifth hop is refused with the reason, a person's input resets, a notice does not, the 21st send in a minute is refused, a text over 128 KiB is refused `too_large`, `from` cannot be forged by a parameter. About 6 tests, 5 s.

**Before S03b is committed (1.3.6): a measurement, not a build.** The config file of a session (`<state>/tools/<session>.mcp.json`, 0600, owned by the person) lies where an agent that runs as the same person with file access (auto mode) can read it, and the `sessions` tool lists the ids that name the files. Such an agent could call the tools as ANOTHER session; today that is the read-only `sessions` list, but from S03b on `send`, `create` and `history` would carry the other session as the one that asks, and the person would approve in its name. It is the same trust domain, so it is a limit and not a bug. Decide with the real program (`claude`, the canary's no-model way): does it need the file after its first successful `initialize` (does `mcp_reconnect`, or a dropped connection, read it again)? If it does not, the host deletes the file after the first connect and the secret lives in two memories only; if it does, the limit is documented in the report and in the approval card text. The brief of the phase review names it too.

## S04 — approvals: `pending` at once, a wake-up input (AC-03, AC-07, SF-01, SF-03)

`send`, `create` and `history` need a person's yes (Deviation 1); **no call is held open (AC-03)**. The call returns at once with text saying: nothing was done yet; the person has been asked; the approval id; "Lico will tell you here when they decide; you can end your turn". A pending record `{id, session, kind, summary, created, expires}` lives in memory in a new module `pending.rs`: at most 8 per session (the ninth is refused `send_limit` with the number); an identical request while one is pending (same kind, target, text hash) returns the same id and adds no card. **The record holds the text it will send** (field `text`: the whole text of `send`, the first prompt of `create`, nothing for `history`; at most 128 KiB). Memory: 8 per session x 128 KiB, at most 64 entries shared with the program's own requests (`MAX_APPROVALS`), so 8 MiB worst case, and therefore **one total cap of 1 MiB of pending text over all sessions**: over it the call is refused `send_limit` with the reason. The text is dropped on decision, expiry, stop and purge. The record shows as a card in the calling session's existing approval list (`add_approval`; the same Y/N keys and window prompt): the card shows tool, target, size and the first line (SF-01, screens note), the key **V** opens the whole text (below), then the person answers. The answers stay `allow` and `deny`; "allow for this session" is the optional field `keep: true` on `approval.answer` (one protocol addition): the call that is answered with `keep: true` still gets its notice (`approved and done`); only the later calls under that keep, per tool and per receiver (a pre-allow to `docs` does not cover `scratch`), run at once and reply with a plain result: no pending, no notice.

**On the decision** Lico performs the action (depth, rate and receiver state are checked again at that moment) and then sends the **notice** to the calling session: `approved and done: ...`, `declined`, `expired`, or `not done: <reason>` (the receiving session is gone, `chain_depth`, ...). The notice is an input with origin `Host`: header `[from lico | 14:02 | approval 7f3a2c]`, echoed like every input (S02b), no hop, it never starts a chain, and a notice does not cause a notice. It uses the delivery function of S03a, so an idle session is woken and a busy one queues it behind its turn.

**Lifetimes.** Expiry is 12 h: a night away is covered, a yes older than half a day answers a question the person no longer remembers, and records are in memory so a host restart ends them anyway. An answer that arrives after the expiry is refused `expired` and the action is not done (tested with the shortened constant); the window's list refresh is itself a check, so with the window open the `expired` notice leaves within one refresh. A stopped or purged session cancels its records and cards; a host restart drops them (the card text says so: "not kept when Lico restarts"). A *disconnected* session keeps them, but an answer is refused `session_disconnected` until the person resumes it (the action would otherwise be done with no one to tell).

**The whole text (SF-01, screens note: key V).** A person who cannot read what they approve cannot protect the receiving session from instructions in the rest of a long text, so the card alone is not enough. Sized minimal: (1) an owner op `approval.text` {session, generation, approval_id, offset, limit} returns one page `{text, offset, next, total}` of the pending text: at most 16 KiB per page, cut on a character boundary, `next` is null at the end, `total` is the byte count (the page size is checked against the socket's reply limit in S04); it is refused `unknown_approval` for a request of the program itself and for a decided one; it is a second protocol v1 addition, with `keep` (schema in `lico_protocol/v1.py` and its contract test; no HTTP route in P03). A text over 16 KiB therefore comes in pages, and nothing is cut silently: the view says `page n of m` and the byte count. (2) The window: a new `gui/cardview.rs` (about 150 lines), a read-only scroll view on the modal frame of S06 (Up/Down, PgUp/PgDn, Home/End; Esc closes; it keeps one page and fetches the next on demand); `Y`/`N` answer from the card as before. (3) The CLI: `lico approval show SESSION N [OFFSET]` prints one page and the next offset; it is also the path of the P test and the fallback if the window part has to wait, and the card names it. Sizes: `pending.rs` +30 lines, `cli.rs` (307) +15, `ipc.rs` (325) +5 (one key list, two checks, one dispatch), `core.rs` 0 (the name joins the existing `OPS` line, `[&str; 30]` becomes 31); no stop line is touched.

**`create`** makes a `claude` session only (SF-05), in the **caller's folder** (or scratch), mode `default`; the prompt shows folder and mode; a different folder or mode is not offered to an agent (alternative: inherit the caller's mode; rejected, an agent in a restricted session would start one that asks for nothing). **Caps:** at most 4 sessions alive at once that agents created per caller, 8 in total; `keep` never lifts them (each session costs 120 to 240 MiB, D4 *measured*); over the cap the call is refused `send_limit` with the numbers. Audit (SF-03): one host-log line per call (tool, session, result), never a body.

**Opt-in real-program check** (not in the suite; haiku, 3 tries): the server answers `pending`, the host later sends the notice; pass = the model ends its turn without polling and the next turn starts from the notice. ## S05 — the whole conversation from the provider's record (SC-03, SC-07)

New module `provider_record.rs`. The program writes its record as one JSON object per line under its own home (`<home>/projects/<folder-key>/<provider-session>.jsonl`); the host knows the home it gave the session and the provider session id, so it looks for `projects/*/<id>.jsonl` and does **not** reproduce the folder-key mangling (fragile). Not found, or the version differs from the pinned one in `capabilities.json`: refuse `record_not_found` with the reason; the window offers, as an explicit second choice labelled so, the host's last records (inputs folded, 2,048 retained). Parsing is defensive and streaming (one line in memory, the output written as it goes): `user` and `assistant` text, `tool_use`, `tool_result` unfolded, images as `[image N KiB]`, a record type it does not know as `[record of type X not shown]`, never an error; the file header states the record range, the date of the first and last record and, when the program itself has compacted its record, says so: a shortened record never looks like the whole. ## S07 — the history and handoff-read tools (AC-02, D4 proposal)

`history` {session, last_n}: the last n (default 100, at most 400 lines or 32 KiB) records of the host record with first and last record number and `older records not shown`; it is the host's record, not the conversation of S05, and it goes through the approval of S04. Tests: P (bounds, path escape, symlink, **a file in another session's inbox is refused by the tool**, a 1 MiB file read in parts equals the file).

## Where this meets the code (corrections to the shape, with the evidence)
- **Answering a card must not run under the caller's lock.** `core::approval_answer` takes the session lock first and then calls `claude::answer`; performing a send locks the receiver, so two sessions answering each other's sends could deadlock. The pending branch is a dispatch of 2 to 3 lines at the top of `approval_answer` (before it locks) that takes the record, drops every lock, performs, and then delivers the notice. `core.rs` (1119, limit 1169) may not grow: the lines are paid for by cuts. Test: two sessions answer each other's pending sends from two threads, both within 5 s (S04).
- **The card text is cut to 200 characters** (`add_approval`) and the list holds at most 64 entries (`MAX_APPROVALS`, shared with the program's own requests); 8 pending per session fits. The card shows tool, target, size and the first line; the whole text is read with the key V (`approval.text`, S04), so a person can read what they approve. The pending text is bounded: 8 x 128 KiB per session, 1 MiB over all sessions.
- **No timer exists for expiry.** It is checked when the list is built, at any tool call of that session and at the next input to it; the `expired` notice leaves at that moment, not at the exact time. Alternative: one sleeper thread per host (16 KiB stack); not chosen. An answer after the expiry is refused `expired`; with the window open its list refresh is itself a check.
- **Tool names.** `read` and `read_file` would sit next to the program's own `Read` tool; they are `history` and `read_handoff` (one table in `mcp.rs`).
- **Who queues a notice behind a running turn.** The program, *measured* in S01c: a message written during a running tool or a pending approval is queued at once and injected at the next tool boundary of the same turn, with one `result`.
- **Hop count of a notice.** Left unchanged on purpose (a person's decision on a card is not a typed input): after a chain of 4 a woken worker can send again only after a person types. The alternative, reset on a notice, lets a chain run on through approvals; not chosen.

## What the second reviewer of P02 teaches this phase (1.3.4)

## How this branch follows P02 (1.3.5)
A phase branch that stands on an earlier, not yet merged phase branch is brought up to that branch by replaying its own unreviewed commits onto the new tip (`git rebase --onto NEW OLD`), checked by `git range-diff` and by the tree of the first replayed commit; the reviewed commits of the earlier phase are never rewritten; a merge commit exists only on `main` and only with the owner's G4 for its exact tree.

Done once so far: after the second reviewer's fix round, the three docs-only commits of this branch (the plan note and its index row) were replayed from `8a0f0e9` onto `b3b8edb`. The six reviewed commits of P02 keep their hashes; `git range-diff` showed the three commits as equal, the change against `b3b8edb` is the plan note and `doc/index_3.md` only, and the tree of the second replayed commit is the tree a merge of `b3b8edb` into the old tip would have given. If the reviewer finds more on P02, the fix goes on the P02 branch and reaches this one by cherry-picks of the fix commits or by repeating the replay (and then the full suite is green at the new tip).

## P06 note
The activity indicator and the attention mark (NT-01) must ignore the echo records (`>> `): a sent, received or notice message is not new output. The window does **not** re-parse prefixes. The host counts the output records that are not echo records, at the one place that appends them, and carries that counter in the session status; NT-01 compares the counter (decided in P06). Alternative: the window skips records that begin with `>> `; wrong whenever an agent's own reply line begins with `>> ` (agent text is recorded raw, so prefix styling in the window is cosmetic and nothing that matters may rely on it).
