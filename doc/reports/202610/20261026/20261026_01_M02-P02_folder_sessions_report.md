## What was built

- **A session runs in a folder the person chooses** (SX-01..03, WK-02..06; slices S02 and S04). `session create --cwd DIR` and the new-session screen: provider, account, folder with the ten recent ones below it, name, model, effort, permission, sign-in, Start. The host checks the folder and gives the reason in the reply: absolute, at most 1,024 bytes, no control character, exists, is a directory, can be listed, and is neither equal to nor inside (links resolved) the registry, log, accounts or credential directories or any scratch workspace. Both providers start in it; a resume with the folder gone is refused with the reason. Models and efforts are read from the installed program's `--help` (here fable, opus, sonnet; low to max), not hard-coded; with no list the screen offers "default" only and says why. The host keeps the last choice and offers it next time. A session shows its name, then its folder, then its id.
- **Delete never touches a chosen folder** (WK-06). The delete code takes no path from the record: it checks the id format, computes `workspace_root/<id>` and removes it only for a scratch session, only if that is a real directory (no link) and a direct child of `workspace_root`.
- **Close, rename, delete** (SX-04..07; S05). `session close` stops the agent and keeps the record, disconnected and resumable (generation checked, idempotent); rename is a record field (60 bytes) shown by every window and the CLI; delete asks first and removes the log and a scratch folder only. Each has a menu entry with its key (F2, Ctrl+Shift+W, Ctrl+Delete), greyed with the reason when it cannot act, and a CLI verb. An idle session is closed at once; one that works, or whose turn waits for an approval, asks first. A deleted session's draft and recall history go with it.
- **One input limit and a real input box** (IN-01..07; S02, S03, S03b). `input` takes up to 64 KiB (newline and tab allowed, no other control character) over the socket, HTTP and the CLI (`-` reads standard input; CRLF and lone CR become LF); the request line and HTTP body limit are 256 KiB, derived from it. The window's box (`gui/editor.rs`) grows to 8 rows and scrolls: Enter sends, Shift+Enter is a newline, cursor keys also by word and line, Delete, Ctrl+Backspace, Ctrl+K, Ctrl+U; a paste is normalised (other control characters left out, one line says how many) and refused whole above 64 KiB with the reason; Up on the first row recalls earlier inputs (20 per session, 256 KiB in all, window memory only); a draft is kept per session and a refused input comes back into the box with one line saying why. S03b: opening one panel from another gave back the draft it took and a half-typed sign-in code is never parked as a draft.
- **The history shows what was sent** (S02b; SC-10 moved here). The host appends a marked copy of every accepted input (`echo.rs`): records start with `>> `, at most 12 lines within 2,048 bytes of line text, then one marker with exact counts that says the agent received all of it. One input costs at most 13 of the 2,048 retained records. It is appended right after a successful delivery under the session lock, so a retry cannot double it, and every shown line passes the same `sanitize` as every other record. All windows, a restart and every kind of session show it the same way. Text that comes from the agent and begins like one of those leads (`>> `, `$ `, `> `, a note of the host) shows `[agent] ` in front of it (F3, below).
- **Memory per session** (MI-01..06; S06). The figure at the right end of a row is what the agent and everything it started hold of their own: `RssAnon` + `RssShmem` summed over the agent and all descendants; RSS travels beside it for the hover text; PSS is not used. Amber from 1 GiB, red from 2 GiB. A line under the list shows sessions, host and window; the hint line under the mouse names the session and says that a program a tool detached with `setsid` is not counted. The host looks lazily: a status call starts a look when the last is older than 3 s, the look runs on its own short thread and never delays the call, and with no window asking nothing is read. A vanished or unreadable process counts for nothing (blank, never an error). The look follows the `children` files of the agents' threads; one `read()` per file; a listing longer than one page (3,500 bytes) is looked at by a scan of `/proc` instead (see Measurements). The list is 330 wide (was 280) so the figure never pushes a title out.
- **Folder trust** (SF-09; S05). Claude is started with `--setting-sources user`, so a chosen folder's own settings (hooks, environment, `.mcp.json`) do not run; its `CLAUDE.md` still applies. See Security. Codex threads start and resume read-only and carry the mode in each turn, so Codex never trusts the folder and never loads its own `.codex/config.toml` (F1, below).
- **Small things on the way.** A suite run the guards refuse (exit 3) leaves no receipt (216a17b); the picture comparisons of `test_frame_cost` leave out the corner that holds the window's own memory total, which can differ by a MiB between two windows (17ab54c, 11afb73).

**Ordering and the echo.** `Session::record_input` appends the echo and then marks the request id accepted, under the session lock, only after delivery succeeded; a retried id echoes nothing; a refused input echoes nothing. The host remembers the last 65,536 request ids of a session (`MAX_TRACKED_INPUTS` in `session.rs`): an id older than that would be delivered again, and so would echo again. (The plan note and two mails said 1,024; that number is the Claude adapter's bound on unacknowledged messages, a different thing. The plan note is corrected in 0.1.2.) What a person sees for a 64 KiB input: twelve `>> ` lines and one marker; for one 64 KiB line: one record of at most 2 KiB and a marker; the captures are in the bundle (`s07_1`, `s07_2`).

## MI-07: what close and delete do to a program the session detached

One real session each (the smallest model, one tool call, answered `allow` only for a prompt that named exactly the command): the session was asked to start `setsid sleep N` and wait 25 s. Result in both runs, `session.close` and `session.purge`: the agent process ends; the detached `sleep` **keeps running**; its parent is `systemd` (it was reparented), it is not in the agent's tree (so it is not in the row's figure either), and its process group and session are its own. It stays until killed; the run killed it by its exact pid after checking its argument vector again. In both runs it sat in the same control group as the host (here the measuring wrapper's scope), so a scope or control group per session, as proposed in MI-07, would hold it and `cgroup.kill` would end it; that is not built. The hint line under a row already says that detached programs are not counted.

### F1: a chosen folder was made trusted by Codex

*The hole.* Codex 0.164.0 treats a project as trusted, and loads its own `.codex/config.toml` (MCP servers, `notify`, hooks, model providers), as soon as a thread's **sandbox can write**: it writes `[projects."<folder>"] trust_level = "trusted"` into its home configuration. In auto mode Lico started threads with `danger-full-access`, so the folder a person chose ran its own commands, and for a session without an account the trust entry went into the person's own `~/.codex/config.toml`. The approval policy plays no part; the sandbox does. (The reviewer found it and the lead reproduced it with the program's own settings and no model call. Claude is not affected: `--setting-sources user`.)

*The fix.* `thread/start` and `thread/resume` always send `sandbox: read-only`; every `turn/start` carries the mode's `approvalPolicy` and `sandboxPolicy` (auto: `never` and `dangerFullAccess`; default: `untrusted` and `readOnly`); one function starts every turn, the fallback after a refused steer included. The window's line about a folder's own settings is now the chosen provider's own (a Codex session was told about `CLAUDE.md`), and `doc/manual_end_to_end.md` says the same.

*Evidence.* The rule test is red on the old code (`f1_red_rule_test.log`: `thread/start` sandbox `danger-full-access`) and green with the fix (13 passed): both modes, create, 12 inputs, close, resume, input; every thread is read-only with the mode's policy, every turn carries it, and the provider's own schema accepts all of it. With the real program and no model call, the old settings load the folder's configuration, run the canary and write a trust entry (`f1_matrix_before.log`); the fixed ones hold in 8 of 8 rows (`f1_matrix_candidate.log`); through the Lico host with the real program, a folder with and one without `.git`, both modes, close and resume: no trust entry, canary 0 (`f1_via_lico_fixed.log`). **Mutation:** the old thread sandbox put back turns the rule test red, and the real program then writes a trust entry and runs the canary 4 times in both kinds of folder (`f1_mutation_writable_thread_sandbox.log`). **Real turns**, once (`codex-cli 0.164.0`, the smallest model, a throwaway folder and home; the sign-in was handled by path only, never read or printed): in auto mode no approval was asked and an `echo`, a file in the folder and a file outside it all exited 0, also after close and resume; in default mode it asked before every command; neither mode wrote a trust entry or ran the canary; the real sign-in file's size and time were unchanged and `codex login status` still said signed in afterwards (`f1_e2e_real_*.log`). ### F3 and F7: what agent text cannot do in the history

`sanitize` (one function, `dropped`, shared by both adapters and the echo) removes U+200B, U+2060 to U+2064, U+FEFF, the tag characters U+E0000 to U+E007F and the bidi controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, U+2028, U+2029); U+200C and U+200D stay (emoji sequences, Persian and Indic shaping). After that, in both adapters, every record that comes from agent text and begins with a reserved lead gets `[agent] ` in front, once: `>> `, `$ `, `> ` and the exact text of every note the host writes itself (the table is every host note text, `[log recovered: ...]` included, which is more than the lead named, because the window reads `[turn ` and the rigs read the exact texts). The decision is made on each resulting record (agent text with newlines is several records; a streamed delta is checked as the line it completes), after the cleaning, on a skeleton of the line (white space and default-ignorable characters taken out), so a zero-width character in front of a marker does not get past it and the check does not depend on a complete list of invisible characters. The tag is added before the record is cut to its bound (`MAX_RECORD`, 4,096 bytes; the 2,048 bytes are the echo's own bound, and echo lines always start `>> `, so there is nothing to tag there).

**What a person sees:** a line of command output that begins like a marker (`$ `, `> `, `>> `, a host note) shows `[agent] ` in front of it. That is the tag working. `> > x` is tagged too (it begins with the `> ` lead; mail 059 said untagged, the lead agreed in 060). Host notes, `$ cmd`, the adapters' `> result` and the echo are not tagged (they have their own leads), and the tool-result `> ` path of `claude.rs` is untouched. **Known limit:** a character that draws as blank but is neither white space nor default-ignorable (for example U+2800) is not seen through by the skeleton, so U+2800 followed by `>> x` stays untagged. The window styles only an exact `>> ` prefix, so that line is not styled as the person's text; a person reading the raw history in a terminal could still be misled.

The Python reference mappings (`codex_mapping.py`, `claude_mapping.py`), which the adapters are tested against, were stale after F7 and F3 (they kept zero-width characters and did not tag). F4b brings them in line (about 35 lines) and one table, `tests/fixtures/provider_text.json`, is read by the Rust unit tests (`leads.rs`), the test of the reference mappings and the test of the built program (`test_forged_leads`). Seven mutations of F3 (`f3_mutation_*`) and eight of F4b (six on the Python mirror, two on the Rust side; `f4b_mut_*`) each turn something red.

### F6: the HTTP listener answers before it reads a body

`http.rs` reads the head first (the same limit and deadline), then checks Host and Origin (403), the credential (401, or 429 when the failed-attempt budget is spent) and the rate limit, and only then reads the body (413 over the limit, 400 on the deadline); every early answer is followed by one `drain` helper, which now also covers the 403, 401 and 429 paths that returned without it. **Behaviour change:** a request that declares a body over the limit and has no credential now gets 401 (it was 413); the test pins it. One HTTP read times out after 5 s (the plan said a 10 s deadline for the head). The test sends exactly a head with `Content-Length: 262144`, no credential and no body, in five cases, each answered in under 3 s; on the old order the answer was 400 after 5 s (`f6_red_http.log`), and with the body read first again the test is red (`f6_mutation_body_first.log`). **Limit:** `drain` stops after 16 reads of up to 500 ms, so a caller that sends one byte every half second after its head holds a connection for up to 8 s; the head itself can be sent as slowly (deadline 10 s, 5 s per read). The listener is optional and bound to the loopback, the window and the command line use the Unix socket, there are at most 32 connections, and a local process can occupy them for about ten seconds each. No code change.

### F10: a closed session's reader could tear down the session resumed after it

*The race.* `session close` followed at once by `session resume` could answer `busy` or leave the resumed session disconnected: the closed provider's reader thread ends a moment after the close, sees the state Running and a link (the new one) and marks the session Disconnected. By hand, 3 of 5 tries with no wait answered `busy`. *The guard* (a few lines in `codex.rs` and in `claude.rs`): the reader acts only when `s.agent_pid == pid`; close and purge zero it, and a resume puts its own process there. I chose the pid guard over a link generation because it is smaller; a pid is not reused while the old child is unreaped, and the window after its `wait()` is not measured.

*Tests.* Red first: 3 failed before the guard (`f10_red.log`): the writable-sandbox rule test without its `sleep(0.5)` answered busy, and both new tests ended `disconnected`, not `running`. The simulators gained `linger:N` (a helper in its own session holds the provider's output open for N tenths of a second, so the old reader ends late on purpose); each adapter has a test that closes, resumes at once, waits 1.6 s and expects `running`, no `[provider disconnected]` and a working input. **Mutation:** the guard taken out of one adapter at a time turns that adapter's new test red (state `disconnected`) and leaves the other adapter's green (`f10_mutation_codex_unguarded.log`, `f10_mutation_claude_unguarded.log`; the lead repeated it). Two limits: "without the guard that rule test answered busy" is true for some runs (my 3 of 5), not for all (in the lead's run it stayed green), so the new tests are the deterministic cover; and `linger:10` is wall clock (the helper lives one second from the start of the turn): in a run where close and resume take longer than a second the old reader ends first and the test cannot fail (said in the test's comment). Existing tests that cover a provider that exits on its own, a close in the middle of a turn and a purge stay green.

## Security

What this phase adds, and what it does not. (1) `status` and the session list now carry each session's folder and name; they are reachable only by what could already read `status` (the 0600 socket of the same user; the loopback HTTP route with its token); the new operations (`session.close`, `rename`, `options`, `input` with a longer text) use the same socket and token, no new listener. (2) A chosen folder is checked in the host (list in "What was built"); nothing in it is ever deleted, and nothing is created in `workspace_root` for it. (3) The first 12 lines or 2 KiB of every accepted input stay in the host log (owner-only) until it rolls over or the session is purged; a purge unlinks the segments, it does not overwrite them (F9: 32 copies of a canary before a purge, none after, both adapters). Before this phase the host log held no input text, so a secret typed into a prompt would land there, bounded, as it does in the provider's own record. (4) `claude --help` is run once (again when the program's modification time changes) with the environment cleared except `PATH` and `LANG`, no account, no network and a 3 s limit; its output is read bounded and only two entries are used. (5) The request limit rose from 4 KiB to 256 KiB per line (only while a line is being read; the connection cap holds; a longer line still gets `too_large` and the connection is closed). (6) Drafts and the recall history live in the window's memory only (`editor.rs` writes no file). (7) `recent_folders.json` (0600, atomic writes) holds ten folders and the last choice (provider, account id, mode, folder, model, effort), validated on read, no credential. (8) **Folder trust:** the program's non-interactive mode skips the question "do you trust this folder", so a chosen folder's hooks, environment and `.mcp.json` ran without anyone deciding. A probe with the real program (three small calls, `trust_probe.log`) showed it: a `SessionStart` hook ran, an MCP server started, and an environment entry redirected the API address to a closed local port (no token left the machine) and hung the call for 100 s. With `--setting-sources user` none of the three ran and the call took 7.4 s; the folder's `CLAUDE.md` was read, and `--settings` (used for the key helper) still applied. The person's own Claude settings still apply to an unbound session. The new-session screen says so in one line. **Still not a sandbox:** the agent runs as the user and can read and write what the user can; "Skip agent prompts" runs tools without asking. (9) **Codex** had the same hole by another door: a writable thread sandbox made Codex trust the folder and load its own configuration; since F1 every thread starts read-only, see F1. (10) The window printed every draft and every sent text to its standard output; since F2 it does so only when `LICO_GUI_EVENTS=1` is set, which the rig sets in one place (the sign-in code is never printed, switch or not). (11) The HTTP listener reads the head and answers 403, 401 or 429 before it reads any body (F6). (12) Text from the agent cannot pass for a person's line, a command, its output or a note of the host: such a line shows `[agent] ` in front (F3); invisible characters are removed from every record (F7) and refused in names and folders (F4). (13) A guard keeps invisible characters out of tracked files (F11).

## Try it yourself (for G3)

You need the `lico` file from the lead's build of the tip and, for items 6 to 10, a Claude Code account you can sign in to (a real turn is billed by the provider). Items 1 to 4 need none. Everything runs on a private socket, so your own host is not touched; the socket path must be short (a Unix socket allows about 100 bytes).

```
T=$(mktemp -d /tmp/lico-try.XXXXXX)
lico host --socket "$T/host.sock" --state-dir "$T/state" --sessions 0 --producing 0 &
export LICO_SOCKET="$T/host.sock"
lico gui --socket "$T/host.sock"          # the window, on the same private host
```

1. **Options come from the program.** `lico session options` prints models (here fable, opus, sonnet), efforts (low to max) and `"recent":[]`. In the window, Ctrl+N shows the same lists.
2. **A folder with a hook.** `mkdir -p "$T/proj/.claude"`; put in `$T/proj/CLAUDE.md` one line naming a code word (say "The code word of this folder is pelican.") and in `$T/proj/.claude/settings.json` a `SessionStart` hook that runs `touch $T/HOOK_RAN` (the shape is the one in the Claude Code settings documentation; the probe used `{"hooks":{"SessionStart":[{"hooks":[{"type":"command","command":"touch /full/path/HOOK_RAN"}]}]}}`). Expected after item 6: `HOOK_RAN` does **not** appear, and the session knows the code word.
3. **Sign in.** `lico account create --provider claude --label Try`, then `lico account login ID` (in the window: Ctrl+A, pick the account, S): the provider's own login runs in that account's private folder under `$T/state`; Lico stores nothing of it. This is the step only you can do.
4. **New-session screen.** Ctrl+N: folder (type it, or take one of the recent ones), name `demo`, model, effort, permission; Tab or Up/Down moves, Left/Right changes a choice, Enter starts. A folder that is not a full path shows "Start session (not yet: the folder must be a full path that starts with /)"; a full path that is not there (`/nonexistent`) is refused by the host with "That folder does not exist." and no session appears. The session row shows `demo` and, at its right end, its memory.
5. **A long prompt.** Type several lines with Shift+Enter, paste a long text (the box grows to 8 rows and scrolls), Enter. The history shows `>> ` lines (at most 12 lines or 2 KiB, then `[N more lines … the agent received all of it]`). Try a paste above 64 KiB: it is refused whole with the reason and the box keeps what you typed.
6. **A real turn.** Ask it to read a file in the folder. Expected: it works in `$T/proj`, `HOOK_RAN` does not exist, the answer knows the `CLAUDE.md` word.
7. **Memory.** Watch the figure grow while it works (a tool adds processes); put the mouse on the row: the bottom line reads like "demo: 126 MiB own (RSS 237 MiB), 3 processes; detached programs not counted; memory shared between processes counts in each", and the line under the list gives the total (`mem sessions …  host …  window …`).
8. **Close.** Ctrl+Shift+W (or Session > Close session): an idle session closes at once; one whose turn is running, or waits for an approval, asks first (Y stops and closes, N keeps it). After a first answer the session stays in the list, disconnected, with its history; Ctrl+R (Session > Resume session) brings it back with the same folder. (Closing a session that has not answered yet says "no conversation to come back to yet"; the CLI prints only `bad_request` for that.)
9. **Rename.** F2 or a double click on the row; type the name, Enter keeps it (an empty name takes it away); a second window (`lico gui --socket "$T/host.sock"`) shows the new name, and so does `lico session list`.
10. **Delete.** Ctrl+Delete (Session > Delete session) asks first; Y deletes. The session goes; `ls "$T/proj"` still lists your files; a session started without a folder had a scratch folder under `$T/state` and that one is gone. Ctrl+Delete here opens the delete question; it is not "delete next word" as in many text fields.

Clean up: `lico --socket "$T/host.sock" host stop --force`, then remove `$T`. The host and CLI commands above were run once against a private socket before this was written (create, rename, delete, options, stop); the window steps are covered by the window tests and the captures in the bundle, not run by hand in your window.

## Known and left

- **Reading the `children` files.** One `read()` per file, a scan above one page; a look can still miss a child that ended just after its pid was printed (the kernel documents the file as fast and cheap, not exact). A missed child takes its subtree with it: the row's figure would dip by that subtree for one look (at most 3 s) and recover. No dip was seen (0 of 600 looks missed a holder).
- **The fork-to-exec copy.** A child between fork and exec holds a copy of its parent's pages and counts with them for that moment: 3 of 200 looks, +5 MiB for a 5 MiB parent, both ways of looking.
- **Shared memory per process.** A shared region mapped by several processes of one tree is counted once for each (so the figure can double it). Probe: private anonymous 103 MiB (`RssAnon`), shared anonymous 99 (`RssShmem`), tmpfs file 99 (`RssShmem`), disk file 106 (`RssFile`, RSS only) for 100 MiB touched each (`s06_shm_probe.log`).
- **Detached programs** (MI-07) are neither counted nor ended; measured above.
- **A heavy child** (a build, a headless browser) was not measured; the simulator's children are Python and the real session's tool processes were `bash` and `sleep`.
- **A host killed with SIGKILL** leaves its agents' descendants running until they end (the cost runs end their host that way and the wrapper stopped 20 held processes each time). An orderly stop is what the product does.
- **`.claude/` under a chosen folder.** Skills, agents and commands there are not "settings" and the probe did not look at them; a skill runs only when the agent or the person calls it. The probe used a closed local port: it shows the redirect works and that no token left the machine, nothing more.
- **Ctrl+Delete** opens the delete question (it asks before it deletes).
- **Small window things:** a long recent folder wraps to column 0; scale 2 was seen in the rig client, not in the real window; Shift+arrows, mouse placement of the caret, undo, caret movement inside the panel and form text fields and Tab completion of folders are not done; the sign-in from the account list now returns to that account's actions.
- **The CLI says only `bad_request`** for closing a session with no conversation yet; the window says why.
- **Lost log.** The first failing run of the memory-reader commit (`test_frame_cost` several-scripts case, 10 pixel rows in the corner) was written to a log name that the rerun reused; that log is gone. The cause is in the commit message of 17ab54c and covered by a test with a mutation log.

- **What the review says the measures do not do** (its six "Not protected" points in plain words): (1) a folder's `CLAUDE.md` and its files still steer the model, and in auto mode a steered model runs commands as the person; nothing here limits what the model does with the folder. (2) A session without an account reads the person's own `~/.claude` or `~/.codex`, so hooks and MCP servers set up there run, and a folder the person trusted earlier in their own `codex` still loads its configuration. (3) A folder above the state directories, such as the home directory, is accepted; only a folder inside them is refused. (4) A program a tool detached (`setsid`) is neither counted in the memory figure nor ended by close or delete (MI-07, measured above). (5) Names, folders and the recent list are stored in plaintext, owner-only (0600). (6) The echo copy of an input is in the host log, next point.
- **The echo copy in the host log (F9).** The first 12 lines or 2 KiB of every accepted input stay in the host log (owner-only) until it rolls over or the session is purged; a purge unlinks the segments, it does not overwrite them.
- **Default mode of Codex.** In default mode the approval is the gate: a command you approve runs with the account's full rights; the read-only sandbox does not confine an approved command (Codex 0.164.0). Not run with Claude, so nothing is said about it.
- **Codex trust is the program's behaviour** (0.164.0), not something Lico can check from inside: the opt-in canary is what notices a change, and it is only as good as the versions tested (`claude` 2.1.310, `codex-cli` 0.164.0). A folder's `CLAUDE.md` or `AGENTS.md` as text is not checked by it: Claude reads `CLAUDE.md`; whether Codex reads `AGENTS.md` in an untrusted folder is unknown.
- **HTTP listener.** `drain` stops after 16 reads of up to 500 ms, so a caller that sends one byte every half second after its head holds a connection for up to 8 s; the head can be sent as slowly (deadline 10 s, 5 s per read). The listener is optional and loopback-bound, the window and the command line use the Unix socket, at most 32 connections; a local process can occupy them for about ten seconds each. No code change.
- **A pid reused between two looks** is counted as the old agent's descendant until the next look (not measured).
- **The `[agent] ` tag.** A line of command output that begins like a marker shows `[agent] ` in front (the tag working). A character that draws as blank but is neither white space nor default-ignorable (U+2800) is not seen through, so U+2800 followed by `>> x` stays untagged.
- **Close, then resume at once (F10).** The pid guard is smaller than a link generation; a pid reuse between the old child's `wait()` and the reader's check is not measured. The new tests are wall clock (see F10).
- **Hidden characters.** A tracked file that is not UTF-8 text is skipped by the guard without a word; today there is none (217 of 217 read).
- **Timing tests under load, and which were re-run alone.** Three tests are sensitive to the load of this shared host. `test_stale_host` (an empty `status` while a host is being replaced): it failed in the changed-run of F4 (`f4_changed_run.log`) and 3 of 6 alone-runs failed before the fix (`f4_stale_rate_1..6.log`) and 8 of 8 passed after it (`stale_after_1..8.log`, about 1.3 s each, load average about 5 by `uptime` at the time; the logs do not hold the load). `test_host_core` (slow subscriber) and `test_activity` (stall) are left as they are, by the lead's word: in the changed-runs of F3, at a load average of 10 to 11 from other jobs, the first failed in the first run (`f3_changed.log`; a re-run of the files that failed, `f3_rerun_three_failed_alone.log`, failed it and both stale-host tests again: 3 failed, 5 passed) and `test_activity` failed its stall test in the second run, in which another test of the file ran 16.0 s against its 15 s budget (`f3_changed2.log`; its stall test passed alone, `f3_activity_alone.log`). In the cold run, at a load average of 4.0 to 4.9, all three passed. I did not measure a rate beyond these runs; read the cold figures with this.
