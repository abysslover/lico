## What was built

- **A session runs in a folder the person chooses** (SX-01..03, WK-02..06; slices S02 and S04). `session create --cwd DIR` and the new-session screen: provider, account, folder with the ten recent ones below it, name, model, effort, permission, sign-in, Start. The host checks the folder and gives the reason in the reply: absolute, at most 1,024 bytes, no control character, exists, is a directory, can be listed, and is neither equal to nor inside (links resolved) the registry, log, accounts or credential directories or any scratch workspace. Both providers start in it; a resume with the folder gone is refused with the reason. Models and efforts are read from the installed program's `--help` (here fable, opus, sonnet; low to max), not hard-coded; with no list the screen offers "default" only and says why. The host keeps the last choice and offers it next time. A session shows its name, then its folder, then its id.
- **Delete never touches a chosen folder** (WK-06). The delete code takes no path from the record: it checks the id format, computes `workspace_root/<id>` and removes it only for a scratch session, only if that is a real directory (no link) and a direct child of `workspace_root`.
- **Close, rename, delete** (SX-04..07; S05). `session close` stops the agent and keeps the record, disconnected and resumable (generation checked, idempotent); rename is a record field (60 bytes) shown by every window and the CLI; delete asks first and removes the log and a scratch folder only. Each has a menu entry with its key (F2, Ctrl+Shift+W, Ctrl+Delete), greyed with the reason when it cannot act, and a CLI verb. An idle session is closed at once; one that works, or whose turn waits for an approval, asks first. A deleted session's draft and recall history go with it.
- **One input limit and a real input box** (IN-01..07; S02, S03, S03b). `input` takes up to 64 KiB (newline and tab allowed, no other control character) over the socket, HTTP and the CLI (`-` reads standard input; CRLF and lone CR become LF); the request line and HTTP body limit are 256 KiB, derived from it. The window's box (`gui/editor.rs`) grows to 8 rows and scrolls: Enter sends, Shift+Enter is a newline, cursor keys also by word and line, Delete, Ctrl+Backspace, Ctrl+K, Ctrl+U; a paste is normalised (other control characters left out, one line says how many) and refused whole above 64 KiB with the reason; Up on the first row recalls earlier inputs (20 per session, 256 KiB in all, window memory only); a draft is kept per session and a refused input comes back into the box with one line saying why. S03b: opening one panel from another gave back the draft it took and a half-typed sign-in code is never parked as a draft.
- **The history shows what was sent** (S02b; SC-10 moved here). The host appends a marked copy of every accepted input (`echo.rs`): records start with `>> `, at most 12 lines within 2,048 bytes of line text, then one marker with exact counts that says the agent received all of it. One input costs at most 13 of the 2,048 retained records. It is appended right after a successful delivery under the session lock, so a retry cannot double it, and every shown line passes the same `sanitize` as every other record. All windows, a restart and every kind of session show it the same way.
- **Memory per session** (MI-01..06; S06). The figure at the right end of a row is what the agent and everything it started hold of their own: `RssAnon` + `RssShmem` summed over the agent and all descendants; RSS travels beside it for the hover text; PSS is not used. Amber from 1 GiB, red from 2 GiB. A line under the list shows sessions, host and window; the hint line under the mouse names the session and says that a program a tool detached with `setsid` is not counted. The host looks lazily: a status call starts a look when the last is older than 3 s, the look runs on its own short thread and never delays the call, and with no window asking nothing is read. A vanished or unreadable process counts for nothing (blank, never an error). The look follows the `children` files of the agents' threads; one `read()` per file; a listing longer than one page (3,500 bytes) is looked at by a scan of `/proc` instead (see Measurements). The list is 330 wide (was 280) so the figure never pushes a title out.
- **Folder trust** (SF-09; S05). Claude is started with `--setting-sources user`, so a chosen folder's own settings (hooks, environment, `.mcp.json`) do not run; its `CLAUDE.md` still applies. See Security.
- **Small things on the way.** A suite run the guards refuse (exit 3) leaves no receipt (216a17b); the picture comparisons of `test_frame_cost` leave out the corner that holds the window's own memory total, which can differ by a MiB between two windows (17ab54c, 11afb73).

The first design scanned all of `/proc` (1,380 processes here): 0.57 % of a core with a window. Following the `children` files of the agents' threads cut it to the figures above; the scan stays as the fallback for a kernel without those files and for a listing past one page. The ten simulated sessions showed 58 to 59 MiB each (the interpreters add their own few MiB to the 45) and the total line `mem sessions 590M  host 1M  window 6M`. Logs: `s07_idle_s1/`, `s07_idle_s2/`, `s07_cost.log`, `s06_cost_scan.log`, `s06_cost_children.log`.

**Does the `children` walk drop a live child?** On one tree whose children start and end all the time, 200 looks each against a scan of `/proc` (`s06_children_vs_scan_30/450/700.out`): 30 alive (4,557 children started): none of 5,747 certainly-alive children missing; 450 alive (10,459 started): none of 87,673; 700 alive (15,637 started): 12 of 200 looks lost a live child; the scan lost none in any of the three. No look missed an anchor (the two long-lived holders), no look fell below 90 % of what they hold. That experiment read each file with one or two `read()` calls; the host first used `fs::read_to_string`, which makes six to nine, each one a new start of the listing, where a child that ended in between can move the index. So the host now reads each file with one `read()` into 8 KiB and scans instead when a listing is longer than one page. `strace` of the old reader, the new one and the measuring script's reader at 40, 450 and 700 children: new reader one `read` (320, 3,600 and 4,088 bytes got), the script one read plus an empty one (700: three), old reader six and nine reads (`s06c2_strace_children.log`). The differential was not rerun through the new reader.

**Ordering and the echo.** `Session::record_input` appends the echo and then marks the request id accepted, under the session lock, only after delivery succeeded; a retried id echoes nothing; a refused input echoes nothing. The host remembers the last 65,536 request ids of a session (`MAX_TRACKED_INPUTS` in `session.rs`): an id older than that would be delivered again, and so would echo again. (The plan note and two mails said 1,024; that number is the Claude adapter's bound on unacknowledged messages, a different thing. The plan note is corrected in 0.1.2.) What a person sees for a 64 KiB input: twelve `>> ` lines and one marker; for one 64 KiB line: one record of at most 2 KiB and a marker; the captures are in the bundle (`s07_1`, `s07_2`).

**Idle and per-session figures of a real Claude session** (haiku, one call per variant, `private/t026/mi07_close.json`, `mi07_delete.json`): before any turn the agent alone is 1 process, 31 to 34 MiB private (76 to 81 MiB RSS); during and right after a turn that ran one shell tool it is 3 processes, 129 to 130 MiB private (242 to 243 MiB RSS). POC-0 measured about 117 to 121 MiB private per idle session after a turn; the figures agree in size, the tree here is three processes and one turn of a different program version. The host stayed at 0.7 MiB private (5.7 MiB RSS) with that session.

## MI-07: what close and delete do to a program the session detached

One real session each (the smallest model, one tool call, answered `allow` only for a prompt that named exactly the command): the session was asked to start `setsid sleep N` and wait 25 s. Result in both runs, `session.close` and `session.purge`: the agent process ends; the detached `sleep` **keeps running**; its parent is `systemd` (it was reparented), it is not in the agent's tree (so it is not in the row's figure either), and its process group and session are its own. It stays until killed; the run killed it by its exact pid after checking its argument vector again. In both runs it sat in the same control group as the host (here the measuring wrapper's scope), so a scope or control group per session, as proposed in MI-07, would hold it and `cgroup.kill` would end it; that is not built. The hint line under a row already says that detached programs are not counted.

## Security

What this phase adds, and what it does not. (1) `status` and the session list now carry each session's folder and name; they are reachable only by what could already read `status` (the 0600 socket of the same user; the loopback HTTP route with its token); the new operations (`session.close`, `rename`, `options`, `input` with a longer text) use the same socket and token, no new listener. (2) A chosen folder is checked in the host (list in "What was built"); nothing in it is ever deleted, and nothing is created in `workspace_root` for it. (3) The host log now keeps the first 12 lines or 2 KiB of every accepted input (file mode 0600; removed with the session on delete): before this phase it held no input text, so a secret typed into a prompt would land there, bounded, as it does in the provider's own record. (4) `claude --help` is run once (again when the program's modification time changes) with the environment cleared except `PATH` and `LANG`, no account, no network and a 3 s limit; its output is read bounded and only two entries are used. (5) The request limit rose from 4 KiB to 256 KiB per line (only while a line is being read; the connection cap holds; a longer line still gets `too_large` and the connection is closed). (6) Drafts and the recall history live in the window's memory only (`editor.rs` writes no file). (7) `recent_folders.json` (0600, atomic writes) holds ten folders and the last choice (provider, account id, mode, folder, model, effort), validated on read, no credential. (8) **Folder trust:** the program's non-interactive mode skips the question "do you trust this folder", so a chosen folder's hooks, environment and `.mcp.json` ran without anyone deciding. A probe with the real program (three small calls, `trust_probe.log`) showed it: a `SessionStart` hook ran, an MCP server started, and an environment entry redirected the API address to a closed local port (no token left the machine) and hung the call for 100 s. With `--setting-sources user` none of the three ran and the call took 7.4 s; the folder's `CLAUDE.md` was read, and `--settings` (used for the key helper) still applied. The person's own Claude settings still apply to an unbound session. The new-session screen says so in one line. **Still not a sandbox:** the agent runs as the user and can read and write what the user can; "Skip agent prompts" runs tools without asking.

## Codex

## Try it yourself (for G3)

You need the `lico` file from the lead's build of the tip and, for items 6 to 10, a Claude Code account you can sign in to (a real turn is billed by the provider). Items 1 to 4 need none. Everything runs on a private socket, so your own host is not touched; the socket path must be short (a Unix socket allows about 100 bytes).

```
T=$(mktemp -d /tmp/lico-try.XXXXXX)
lico host --socket "$T/host.sock" --state-dir "$T/state" --sessions 0 --producing 0 &
export LICO_SOCKET="$T/host.sock"
lico gui --socket "$T/host.sock"          # the window, on the same private host
```

1. **Options come from the program.** `lico session options` prints models (here fable, opus, sonnet), efforts (low to max) and `"recent":[]`. In the window, Ctrl+N shows the same lists.
2. **A folder with a hook.** `mkdir -p "$T/proj/.claude"`; put in `$T/proj/CLAUDE.md` one line naming a code word (say "The code word of this folder is pelican.") and in `$T/proj/.claude/settings.json` a `SessionStart` hook that runs `touch $T/HOOK_RAN` (the shape is the one in the Claude Code settings documentation; the probe used `{"hooks":{"SessionStart":[{"hooks":[{"type":"command","command":"touch /full/path/HOOK_RAN"}]}]}}`). Expected after item 6: `HOOK_RAN` does **not** appear, and the session knows the code word.
3. **Sign in.** `lico account create --provider claude --label Try`, then `lico account login ID` (in the window: Ctrl+A, pick the account, S): the provider's own login runs in that account's private folder under `$T/state`; Lico stores nothing of it. This is the step only you can do.
4. **New-session screen.** Ctrl+N: folder (type it, or take one of the recent ones), name `demo`, model, effort, permission; Tab or Up/Down moves, Left/Right changes a choice, Enter starts. A folder that is not a full path shows "Start session (not yet: the folder must be a full path that starts with /)"; a full path that is not there (`/nonexistent`) is refused by the host with "That folder does not exist." and no session appears. The session row shows `demo` and, at its right end, its memory.
5. **A long prompt.** Type several lines with Shift+Enter, paste a long text (the box grows to 8 rows and scrolls), Enter. The history shows `>> ` lines (at most 12 lines or 2 KiB, then `[N more lines … the agent received all of it]`). Try a paste above 64 KiB: it is refused whole with the reason and the box keeps what you typed.
6. **A real turn.** Ask it to read a file in the folder. Expected: it works in `$T/proj`, `HOOK_RAN` does not exist, the answer knows the `CLAUDE.md` word.
7. **Memory.** Watch the figure grow while it works (a tool adds processes); put the mouse on the row: the bottom line reads like "demo: 130 MiB of its own (RSS 243 MiB), 3 processes; a program a tool detached is not counted", and the line under the list gives the total (`mem sessions …  host …  window …`).
8. **Close.** Ctrl+Shift+W (or Session > Close session): an idle session closes at once; one whose turn is running, or waits for an approval, asks first (Y stops and closes, N keeps it). After a first answer the session stays in the list, disconnected, with its history; Ctrl+R (Session > Resume session) brings it back with the same folder. (Closing a session that has not answered yet says "no conversation to come back to yet"; the CLI prints only `bad_request` for that.)
9. **Rename.** F2 or a double click on the row; type the name, Enter keeps it (an empty name takes it away); a second window (`lico gui --socket "$T/host.sock"`) shows the new name, and so does `lico session list`.
10. **Delete.** Ctrl+Delete (Session > Delete session) asks first; Y deletes. The session goes; `ls "$T/proj"` still lists your files; a session started without a folder had a scratch folder under `$T/state` and that one is gone. Ctrl+Delete here opens the delete question; it is not "delete next word" as in many text fields.

Clean up: `lico --socket "$T/host.sock" host stop --force`, then remove `$T`. The host and CLI commands above were run once against a private socket before this was written (create, rename, delete, options, stop); the window steps are covered by the window tests and the captures in the bundle, not run by hand in your window.

## Known and left

- **Reading the `children` files.** One `read()` per file, a scan above one page; a look can still miss a child that ended just after its pid was printed (the kernel documents the file as fast and cheap, not exact). A missed child takes its subtree with it: the row's figure would dip by that subtree for one look (at most 3 s) and recover. No dip was seen (0 of 600 looks missed a holder).
- **The fork-to-exec copy.** A child between fork and exec holds a copy of its parent's pages and counts with them for that moment: 3 of 200 looks, +5 MiB for a 5 MiB parent, both ways of looking.
- **Shared memory per process.** A shared region mapped by several processes of one tree is counted once for each (so the figure can double it). Probe: private anonymous 103 MiB (`RssAnon`), shared anonymous 99 (`RssShmem`), tmpfs file 99 (`RssShmem`), disk file 106 (`RssFile`, RSS only) for 100 MiB touched each (`s06_shm_probe.log`).
- **Detached programs** (MI-07) are neither counted nor ended; measured above.
- **A heavy child** (a build, a headless browser) was not measured; the simulator's children are Python and the real session's tool processes were `bash` and `sleep`.
- **A host killed with SIGKILL** leaves its agents' descendants running until they end (the cost runs end their host that way and the wrapper stopped 20 held processes each time). An orderly stop is what the product does.
- **`.claude/` under a chosen folder.** Skills, agents and commands there are not "settings" and the probe did not look at them; a skill runs only when the agent or the person calls it. The probe used a closed local port: it shows the redirect works and that no token left the machine, nothing more.
- **Ctrl+Delete** opens the delete question (it asks before it deletes).
- **Small window things:** a long recent folder wraps to column 0; scale 2 was seen in the rig client, not in the real window; Shift+arrows, mouse placement of the caret, undo, caret movement inside the panel and form text fields and Tab completion of folders are not done; the sign-in from the account list now returns to that account's actions.
- **The CLI says only `bad_request`** for closing a session with no conversation yet; the window says why.
- **Lost log.** The first failing run of the memory-reader commit (`test_frame_cost` several-scripts case, 10 pixel rows in the corner) was written to a log name that the rerun reused; that log is gone. The cause is in the commit message of 17ab54c and covered by a test with a mutation log.
